# mtroamd 1.4.2 Codex Security Audit Follow-Up

Date: 2026-05-27
Reviewer: Codex
Scope: Focused follow-up review of the fixes made after `docs/1.4.2-codex-security-audit.md`.

## Executive Summary

The original findings were materially addressed, but one recover concurrency edge remains.

The recover path now has:

- a per-session recovery slot via `Session.TryStartRecover`;
- cancellation of the previous recovery when a new one starts;
- a 2 minute maximum recovery grace window;
- a 4096 byte maximum custom save prompt.

The peer-address logging mismatch was addressed by updating `docs/SECURITY.md` to document that peer addresses are logged, rather than promising masked IPs.

## Follow-Up Findings

### MEDIUM: Recover cancellation slot can be cleared by an older canceled recovery

**Status: RESOLVED 2026-05-29 (commit fb353b6).** The clear is now
identity-aware via a generation token — see "Resolution" below.

References:

- `internal/session/session.go`: `TryStartRecover` cancels any existing recovery and stores the new cancel function in `s.recoverCancel`.
- `internal/session/session.go`: `ClearRecover` unconditionally sets `s.recoverCancel = nil`.
- `internal/transport/pumps.go`: each recover goroutine defers `sess.ClearRecover()`.

Impact:

The new recovery slot prevents unbounded simultaneous recoveries in the common case, but it is vulnerable to this interleaving:

1. Recover A starts and stores cancel A.
2. Recover B starts, cancels A, and stores cancel B.
3. Recover A observes cancellation, returns, and its deferred `ClearRecover` sets `recoverCancel = nil`.
4. Recover B is still running, but the session no longer has a cancel function for it.
5. Recover C starts and cannot cancel B because the slot was already cleared.

That reopens overlapping recover behavior after a replacement race, especially around the early cancellation checkpoints and timer windows.

Recommended fix:

- Make the clear operation identity-aware. For example, have `TryStartRecover` return both `ctx` and `cancel`, then call `ClearRecover(cancel)` and clear only if the stored cancel still matches that recovery.
- Alternatively, track a monotonically increasing recovery generation and clear only when the finishing goroutine's generation matches the active generation.
- Add a unit test that starts recovery A, starts recovery B, clears A, then verifies starting recovery C cancels B.

Resolution (commit fb353b6):

- `Session.TryStartRecover` now returns `(context.Context, uint64)` — a
  context plus a monotonic generation token — and increments
  `recoverGen` each call. Function values aren't comparable in Go, so
  the slot's owner is tracked by generation rather than by the cancel
  func itself (the auditor's "match the stored cancel" can't be done
  literally).
- `Session.ClearRecover(gen)` frees the slot only when `gen ==
  s.recoverGen`. A superseded recovery finishing with a stale
  generation is a no-op, so it can no longer free the slot its
  successor owns.
- `internal/transport/pumps.go` threads the generation through the
  deferred `sess.ClearRecover(gen)`.
- Regression test `TestClearRecoverStaleGenerationDoesNotFreeSuccessor`
  (`internal/session/session_test.go`) reproduces the A/B/C interleave;
  verified failing without the generation guard and passing with it.
  Full `internal/session` + `internal/transport` suites pass under
  `-race`.

## Resolved Or Accepted Items

### Recover grace and prompt bounds: addressed

`internal/transport/recover.go` now caps `GraceMillis` with `maxGrace = 2 * time.Minute` and truncates `SavePrompt` to `maxSavePromptLen = 4096`.

### Recover no longer only starts detached unbounded work: partially addressed

`internal/transport/pumps.go` now calls `sess.TryStartRecover()` and runs `runRecover` with the returned context, so new recover requests cancel the previous recovery. The remaining issue is the stale `ClearRecover` race described above.

### Peer-address logging documentation mismatch: addressed by documentation

`docs/SECURITY.md` now says attach events log `session ID, peer address`. The implementation still logs full remote addresses in transport connection paths, but the documentation no longer promises masked IPs.

### Tailnet TCP help text mismatch: addressed

`cmd/mtroamd/serve.go` now describes deferred `tailnet:` startup and polling behavior instead of saying the daemon exits when Tailscale is unavailable.
