# meshtermd 1.4.2 Codex Security Audit

Date: 2026-05-27
Reviewer: Codex
Scope: Static pre-release security review of the current `meshtermd` repository, focused on daemon transport, attach/recover control flow, local IPC, TCP roaming fallback, update verification, service unit generation, and documented security posture.

## Executive Summary

No release-blocking critical issues were found in this static pass.

The main remaining security concern is the recover control path. An authenticated exclusive client can enqueue multiple detached recovery sequencers for the same session, each with attacker-controlled grace timing and prompt text. That is not a remote unauthenticated break, but it is a practical session-disruption and resource-retention vector for a stolen token, buggy client, or already-authorized peer.

I also found one low-severity privacy/documentation mismatch: `docs/SECURITY.md` promises masked peer IPs in attach logs, while the connection handler logs the full remote address.

## Findings

### MEDIUM: Recover requests can create unbounded detached session work

References:

- `internal/transport/pumps.go`: `TypeRecover` accepts recovery control frames from exclusive clients and starts `go runRecover(context.Background(), sess, m, write)`.
- `internal/transport/recover.go`: `runRecover` uses `req.SavePrompt` directly, defaults only when empty, and derives `grace` from `req.GraceMillis` without an upper bound.
- `internal/protocol/protocol.go`: `Recover` exposes `SavePrompt string` and `GraceMillis uint32`.

Impact:

An authenticated exclusive client can repeatedly send `Recover` frames. Each frame starts a detached goroutine using `context.Background()`, so disconnecting the client does not stop the sequence. Because there is no per-session singleflight, cancellation of previous recovery attempts, grace clamp, or explicit prompt-size policy beyond the protocol frame limit, a malicious or malfunctioning authorized client can:

- accumulate long-lived goroutines and timers, especially with large `GraceMillis` values;
- schedule multiple delayed PTY injections against the same session;
- repeatedly inject custom prompt content, `/exit`, and `claude --resume` into an active session;
- cause confusing or destructive user-visible interleaving when recoveries overlap.

The auth boundary matters: this requires an attach token and exclusive access. It is still worth fixing before release because recover intentionally drives the user's interactive shell and should be idempotent per session.

Recommended fix:

- Add per-session recovery state so only one recovery can run at a time.
- Prefer rejecting a second recover with a `RecoverProgress` error, or cancel and replace the prior recovery explicitly.
- Cap `GraceMillis` to a small operational maximum, for example 2 minutes.
- Cap `SavePrompt` to a deliberate limit smaller than the frame maximum.
- Add tests covering duplicate recover requests, grace clamping, and cancellation/rejection behavior.

### LOW: Security documentation says peer IPs are masked, but logs contain full remote addresses

References:

- `docs/SECURITY.md`: says attach events log the session ID and peer IP with the last two IPv4 octets masked.
- `internal/transport/protocol_handler.go`: creates the per-connection logger with `remote`, `ctrl.RemoteAddr().String()`.
- `internal/transport/handler.go` and `internal/transport/tcp_server.go`: also log full remote addresses in connection handling paths.

Impact:

Deployments using systemd journal or collected logs may retain full client IP addresses even though the security documentation promises masked addresses. This is not a protocol break, but it is a privacy and compliance mismatch.

Recommended fix:

- Either mask remote addresses before logging, including TCP and QUIC paths, or update `docs/SECURITY.md` to state the actual logging behavior.
- If masking is intended, handle IPv4, IPv6, host:port formatting, and parse failures consistently.

## Operational Notes

- `cmd/meshtermd/serve.go` help text says a `tailnet:` TCP bind exits when no Tailscale interface is found. Current daemon behavior appears to defer TCP startup and poll until the tailnet is available. Align the help text with the implemented deferred behavior.
- The canonical user unit now defaults `--roam-tcp-addr tailnet:49920`, which is a better default than binding fallback TCP broadly.
- Explicit TCP bind exhaustion appears to degrade to no TCP listener rather than failing daemon startup. That is primarily an availability/operator-surprise issue, not a direct security finding.

## Positive Security Observations

- Local IPC socket creation verifies parent directory ownership and permissions, rejects symlinked socket paths, and chmods the socket to `0600`.
- Certificate and key state is written under a verified per-user state directory, with private key permissions set to `0600`.
- TCP fallback has a short pre-auth read deadline and the user-unit default prefers a tailnet-scoped bind.
- The update path validates version tags, prevents downgrade by default, verifies minisign signatures and trusted comments, checks checksums, and caps download sizes.
- The documented SSH bootstrap TOFU caveat is explicit and matches the `StrictHostKeyChecking=accept-new` implementation.
- Sidecar control sockets and environment files are placed under per-user state paths with restrictive permissions.

## Verification

- Static review: completed.
- `go test ./...`: not run successfully because the `go` binary is not installed in this environment (`/bin/bash: line 1: go: command not found`).

## Suggested Pre-Release Gate

For v1.4.2, I would treat the recover concurrency issue as the only fix-before-release item from this pass if recovery is enabled in production clients. If recovery is still experimental or hidden behind an explicit manual action, it can be documented as a known risk, but the implementation should still get per-session singleflight and grace clamping soon.
